# 智能班级助手接入

目标：可设置表达风格；用自然语言记录考勤、表扬；用本机OCR识别名单图片；把图片文字、粘贴文本和表格整理成可核对的学生导入预览。

## 运行方式

- Dify 工作流负责理解指令、选择已注册工具和形成回答；Java 后端继续负责身份、权限、校验、事务和实际保存。
- `agent/class-agent.workflow.yml` 是可导入的工作流模板。输入 `request_json`，输出字符串 `reply`，内容为结构化工具调用或最终回答。
- 不向Dify开放数据库连接或任意SQL。工作流的指令必须经过现有工具白名单，不能新增未知操作。
- 首次使用在Dify选择已有密钥支持的快速文本模型。模板默认 `deepseek-flash`；实际模型以Dify中可用配置为准，禁用深度思考以减少常规指令等待。图片由Windows OCR本机转文字，不需要额外视觉模型。
- SSE持续显示当前处理进度，最后返回完整结论和数据库结果；当前不逐字输出结构化规划JSON。

## 本机部署

1. 安装WSL2，启用Virtual Machine Platform；Windows要求重启时先重启，再启动Docker Desktop。
2. `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Deploy-DifyLocal.ps1` 使用已下载的固定官方版本部署；已有`.env`和数据不会被覆盖或清空。
3. 打开 `http://127.0.0.1:8188` 完成Dify初始化。在模型供应商中配置文本模型，密钥仅在本机输入。
4. 在Dify中从DSL导入 `agent/class-agent.workflow.yml`，选择正确模型并发布。测试输入为 `{"messages":[{"role":"user","content":"你好"}],"tools":[]}`。
5. 创建该应用的API Key，在本机执行 `scripts/Configure-Dify.ps1` 隐藏输入，使用DPAPI加密保存。不要发到聊天或提交Git。
6. 执行 `scripts/Start-AgentLocal.ps1`。默认必须配置Dify，读取本机DPAPI密钥并通过子进程环境传递。`/api/ai/status` 显示当前引擎及配置状态；不会在Dify故障时偷偷切换引擎。

启动脚本只复用既有3310演示库，不连接3306原库，不重新初始化数据库，不终止已有服务。Dify部署受阻时，只有显式传入 `-Engine deepseek` 才继续使用此前配置的DeepSeek模型，适用于独立验证人设、OCR和现有业务操作，不代表Dify已接通。

Docker运行数据位于 `%USERPROFILE%\ClassManagementAgent\dify`，避开OneDrive项目目录。此机器原AppData目录带有EFS属性，Docker设置的原子重命名因此失败；`scripts/Start-DockerLocal.ps1`仅为Docker子进程设置独立运行目录 `%USERPROFILE%\ClassManagementAgent\DockerRuntime`，不改变Windows全局环境变量。两个桌面的Docker快捷方式已使用该启动脚本。管理端口仅绑定本机。首次拉取镜像需要网络和额外磁盘空间。

## 使用与校验

- 在“助手设置”中选择干练、温和、鼓励三种风格或补充自定义人设，偏好按当前账号保存在浏览器。
- “今天一班张三迟到了，给我记上”：本轮明确提供的学生、日期、考勤类型均通过校验，且没有疑似重复时，才允许自动保存。否定、疑问、歧义或无法证明参数来自原文的情况仅生成预览，不自动写入。
- Excel/CSV直接走本地解析、表头映射和已有导入校验，不经过模型重新抄写全表。目标班级可手动选择；非空的原班级不会被目标班级覆盖。
- 图片支持PNG/JPG；上传后先核对OCR文字，特别是姓名、学号。系统不承诺模糊或手写名单的识别准确率。缺失学号必须补齐，模型不能自行编造。
- 名单与批量成绩始终先预览、后确认。正式学生导入仍由管理员执行；教师可以查看预览。
- 写入结果以后端返回的记录为准，网络中断后不要把未确认状态描述为已保存。

## 2026-11-17 端口调整与引擎选择

**端口**：Dify 的 nginx 原来映射到宿主机 `8088`，本机被 Clash Verge 的代理内核 `verge-mihomo` 占用了这个端口，容器重建时报 `bind: An attempt was made to access a socket in a way forbidden by its access permissions`，表现为「Docker 明明起来了但助手还是连不上」。现改为 `8188`：

- `dify/docker/.env`：`EXPOSE_NGINX_PORT=127.0.0.1:8188`，`CONSOLE_API_URL`/`CONSOLE_WEB_URL`/`SERVICE_API_URL`/`APP_API_URL`/`APP_WEB_URL` 同步改为 `http://127.0.0.1:8188`。原文件备份为 `.env.bak-20261117-8088`。
- 后端地址记录在 `.secrets/dify-url.txt`，已改为 `http://127.0.0.1:8188/v1`。
- 改完执行 `docker compose -p class-agent -f docker-compose.yaml -f class-agent.local.yaml up -d`，用 `docker port class-agent-nginx-1` 确认映射生效（应显示 `80/tcp -> 127.0.0.1:8188`）。

排查要点：`docker ps` 显示容器 Up 不代表端口可用；`docker port` 输出为空才是真信号。

**引擎默认值**：`Start-AgentLocal.ps1` 的 `-Engine` 默认值由 `dify` 改为 `deepseek`。理由是不再要求 Docker 与工作流同时就绪，少一层依赖；需要 Dify 时显式传 `-Engine dify`。

**额度提示**：Dify 工作流里模型报 402 时，后端原来只说「工作流未完成，请稍后重试」，容易被当成网络问题。现在识别 `Insufficient Balance` 与 402，直接提示「模型账户余额不足，请充值后重试」。DeepSeek 直连同样把 402 映射为「DeepSeek 额度不足」。

**当前状态（2026-11-17）**：Dify 容器与 8188 链路均正常，工作流可执行到调用模型这一步；DeepSeek 账户余额不足（402），因此两条通道都无法返回模型回答。这是账户问题，不是部署问题——充值即恢复。
