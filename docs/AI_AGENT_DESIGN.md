# AI Agent设计


## 接入与意图识别

DeepSeekClient使用Java HttpClient向配置的官方兼容/chat/completions发送model/messages/tools/max_tokens，thinking关闭。默认地址https://api.deepseek.com，模型deepseek-flash；密钥只在后端进程。无Key时拒绝AI调用，普通业务照常运行；不将Key放前端、仓库或日志。

复杂自然语言意图由模型选择注册函数与结构化参数，后端不把模型参数当作可信数据。目标明确的最高分查询和简短考勤登记先由AiLocalCommands在本机处理，不能完整识别、有多名学生、未知班级、额外原因等情况再交给模型。AiController控制认证用户会话、输入长度、历史、超时、轮数和重复调用；模型回答不得代替数据库结果。没有额外训练模型，未测整体意图识别准确率。

回复先给用户要的姓名和分数，不主动讲得分率、权重、统计口径。未指定考试的只读最高分查询默认最近一次已有成绩的共同考试，并简短带出考试名；确实需要澄清时只问一个关键问题，不强制“请补充”前缀。普通聊天、解释及写作仍由Dify模型回复。

score_leaders支持同场考试的单科原始分，或语文、数学、英语三科直接相加的总分。后端验证各班同场考试、各科满分一致，缺考和缺科不进入总分排名，同分并列。不会把普通总分误当作需要额外权重的综合评价。最高分、明确月份/考试名的查询可在本机执行；姓名、复杂范围或意图有歧义时交给模型进一步核对。本地考勤也调用原有WriteTools与canAutoRecord，重复及歧义继续等待确认，没有跳过校验或新增数据库权限。

查询链：网页 → JWT → AiController → DeepSeekClient → Tool Calls → ReadOnlyTools → 实际Service → 数据库/统计 → 结构化结果与模型文字 → 网页。用户可展开真实工具结果，均分/排名/完成率来自Service。

## 白名单和身份

模型可用工具为query_school、prepare_school_write、prepare_student_import、reply_to_user，管理员还可使用query_recycle_bin。不能执行任意SQL/系统命令。kind由封闭枚举分派，未知字段、类型、日期、工具名和不支持的组合拒绝。所有SQL由后端固定并参数绑定，回收数据的表名仅来自后端八种固定类型，恢复字段经过白名单校验。

reply_to_user只返回普通聊天文字，不访问业务数据库。问候、倾听、一般知识、写作及建议可直接自然回答，复用现有会话上下文及人设，一次模型请求结束，不强制追问班级或学号。实际业务事实仍须本轮query_school结果，业务写入仍由原有预览/确认及自动记录校验执行。该回复通道只允许一个answer字段，不接收SQL或操作参数；模型不得用普通回复虚构数据库事实或已保存状态。没有联网搜索能力，不承诺实时信息。会话仍为内存中最近若干轮，闲置30分钟过期，不提供永久记忆。

query_school支持students、classes、exams、scores、score_statistics、assignment_catalog、assignments、assignment_statistics、attendance、attendance_statistics、praises、praise_statistics。先按明确姓名/学号定位，本轮resolved集合限制猜studentId。同名后端直接返回候选并停止；本轮修复姓名无匹配仍继续调用模型的问题，无匹配由后端直接安全返回。不存在学号由Service拒绝。个人作业状态使用assignments，不能用作业目录或全班统计替代。

日期按Asia/Shanghai，支持明确起止范围及已注册相对表达；不能混合或猜不明确日期。成绩统计必须指定考试，作业统计必须指定作业；exams只接收classId，不支持日期参数。工具说明已补足这些限制，后端严格校验保留。

## 写入、确认与审计

prepare_school_write生成预览：attendance_add、attendance_edit、assignment_state、praise_add、praise_edit、scores_add，以及管理员的recycle_delete、recycle_restore。管理员可移除班级、学生、考试、作业、成绩、作业记录、考勤和表扬，数据进入按类型分类的回收站。删除班级或学生时关联记录同批保存；支持单条及整组恢复，保留原编号和外键顺序。没有永久删除、任意SQL、考试创建或成绩覆盖工具。考勤修改限指定记录备注，表扬修改指定记录原因/备注，作业修改明确学生/作业状态，完成必须实际submittedAt。

删除和恢复先查询本轮真实编号，AiController校验目标来自对应的活动查询或回收查询；不接受猜测编号。预览展示各类型数量、总数和规则，并保存快照指纹。确认时重新锁定目标、核对指纹，变动则拒绝；删除或恢复均以事务执行，恢复冲突整批回滚，不覆盖当前数据。删除与恢复不纳入自动考勤保存，必须点击确认。直接学生、班级、考勤和表扬删除接口也改为回收；恢复接口与回收站只允许ADMIN。AI仍依赖模型理解，类型或名称不清楚时应补充信息，不能保证任意表述一次识别成功。

学号按StudentService.normalizeNo校验，允许1至50位字母、数字、下划线、短横线，没有固定长度或年份前缀。提示词明确26等短学号按原值处理，交后端做唯一性检查；名单仍由管理员核对后导入。

预览持久化ai_operations，包含认证用户、目标、参数、修改前快照、重复提醒和15分钟有效期；界面明确尚未保存。网页通过独立/api/ai/operations/{id}/confirm人工确认，模型没有确认工具。取消仅改预览状态，网络超时先刷新实际状态，不盲目重试。

WriteTools确认时锁定本人操作和目标，重建预览、比较快照，再调用AttendanceService/AssignmentService/PraiseService/ScoreService。业务变更和成功结果同事务；失败整批回滚后记FAILED与安全原因。重复/并发确认返回原结果，不重复写。ADMIN/TEACHER仅可确认本人预览；传统写接口仍ADMIN。尚无按任教班级隔离。

ai_operations兼作操作审计，记录ID、user_id/owner、kind/status、payload/preview、result/failure、时间与过期时间；保留修改前后信息，普通聊天不能修改审计。不是所有传统管理操作的统一审计系统，不宣称具备完整全站操作日志。日志和审计不保存Key/密码/完整聊天；用户输入的备注仍需避免粘贴秘密。

## 批量成绩

先选真实存在的考试，明确科目和满分。scores_add顶层仅kind/examId/subject/fullScore/rows，学生身份只在行内；每行仅name/studentNo/score。行数1–100，严格参数/班级/满分/分数/唯一性校验；未知学生、同名、重复行、已有成绩列为错误或跳过，不自动创建学生、考试或覆盖成绩。

预览显示身份、考试、科目、得分/满分、状态和原因，有效行待人工确认。确认时重新校验所有目标和快照，有效行同事务提交，数据库故障整批回滚。幂等结果保存在操作表。文件成绩导入和AI成绩预览是两条入口，均不能以客户端伪造预览内容确认写入。

## 实际限制

模型可能遗漏复合问题、删去姓名中的括号、传入某kind不支持的字段，或提前查询不存在的批次学号导致安全失败；本轮真实失败记录保留。补充工具说明降低歧义，但不构成准确率保证。演示时使用明确学号、具体日期、考试ID和短问题，核对预览后再确认。

没有跨考试可比性/综合权重，不声称自动进步排名或综合评分；没有模型自动修改任意业务记录、自动删除、自动确认或多实例共享会话。未进行广泛提示注入/渗透或长期稳定性测试。真实验证通过的范围以最终报告为准。

## 自动记录：让助手直接写库的边界

助手设置里有一个开关「明确的考勤、表扬指令校验后直接保存」，默认开启。开启后，符合条件的指令不再生成待确认预览，而是校验通过即落库，回复「已保存某某的考勤记录」。

### 触发条件（`AiRosterService.canAutoRecord`）

必须**同时**满足，任一不满足就退回人工确认：

1. 操作类型只限 `attendance_add` 或 `praise_add`
2. 消息里出现明确写入动词；考勤认「记上/记录/登记/添加/记一下/记一次/记一笔/登一下/录一下/录入」，表扬另外认「表扬/奖励/加分」
3. 不含排除或探询词：不要、别记、取消、假如、如果、是否、有没有、查询、看看、会不会、能不能
4. 该记录没有疑似重复（同日同类型已有记录时不直存）
5. 消息里出现学生姓名或学号
6. 日期明确：消息里含具体日期，或含「今天/昨天」且与解析结果一致
7. 考勤必须明说类型（迟到/早退/缺勤）；表扬必须给出原因且原因出现在原话里
8. 消息里若提到班级，必须唯一匹配且与学生所属班级一致；**没提班级时不作要求**（学生身份已由姓名或学号校验）
9. 只处理单条指令

### 为什么不放开更多

- **成绩**：需先查考试、满分和科目，一处错就写错分，且没有"删掉重来"的顺滑体验。
- **作业状态**：完成时间必须是真实时刻，模型容易编造。
- **删除与恢复**：不可逆感最强，且需要用户在多个同名记录里选择。
- 这三类继续走「生成预览 → 网页点击确认」，预览 15 分钟有效，可取消。

### 2026-11-18 的修正

这个开关此前**几乎从不生效**，三处缺陷：

- `classId` 校验过严：只要参数里带了班级 ID，就要求消息原文也出现该班级。而用户说「给黄梓晨记一次迟到」通常不会提班级，模型查出班级反而导致拒绝。改为消息未提班级时不校验。
- 动词白名单缺「记一次」「记一笔」等常见说法，只认「记一下」。
- 表扬类指令的自然说法是「表扬某人」，但白名单是给考勤设计的，导致表扬永远无法直存。现按操作类型分别匹配动词。

另修一处参数兼容：模型有时把备注写成 `reason` 而非 `remark`，`attendance_add` 原先直接 400 拒绝，现两者都接受。

复测（2026-11-18）：`给张浩然记一次迟到，昨天早上7点40，原因堵车` → SUCCEEDED，考勤 +1；`表扬张浩然，理由是拾金不昧，昨天` → SUCCEEDED，表扬 +1；`删除黄梓晨今天那条考勤` 仍返回待确认；`记一下黄梓晨迟到`（缺日期）被无依据保护层拦下。

## 无依据保护层的边界（2026-11-18）

模型选择不调用任何工具时，后端对它的回答做一次判定：

- **闲聊、反问、拒绝**：直接采纳。早先这里一律替换成「尚未取得本轮数据库查询结果」，结果连「你好」都回不了。
- **宣称已执行写操作**：若回答里出现「已删除/已保存/已修改/已添加/已录入/已更新/已提交/已恢复/已移入」而本轮既无查询结果也无写入预览，替换成提示。这是防止模型编造操作结果。

试过 `tool_choice: required` 强制模型必选工具，寒暄问题能解，但会让本该拒绝或反问的请求被强行推进工具链，拒绝类通过率从 10/10 掉到 5/10，已回退。宁可保留这层精确拦截。

## 工具错误的处理（2026-11-18）

模型调工具时参数写错，原先会让整个请求以 HTTP 400 结束，网页上弹出「AI 工具包含未知参数」。这在 LLM 应用里是反模式：模型看不到自己的错误，用户也不知道该怎么办。

现在分两类：

- **字段或取值不对**（未知参数、枚举越界、必填缺失、目标未确认等）：把错误作为工具结果回给模型，让它按错误信息修正后重试；修不好就让它用 `reply_to_user` 向用户说明缺什么。用户看到的是正常对话。
- **参数根本不是合法 JSON、或同一查询重复发起**：仍然直接报错。这两类重试无益——前者是模型生成能力问题，后者是防死循环的去重机制。

安全不因此削弱：每次重试都重新走同一套白名单和校验，错误信息只回给模型，不会绕过任何检查。

## 会话上限（2026-11-18）

原先每用户最多 5 个会话、系统总上限 200，超出直接报「会话数量已达上限」。实测点几次「新建对话」就撞上限。

现在每用户 20 个，达到时自动淘汰自己最旧的一个；系统级 400 个，同样淘汰最旧的。会话本身仍是内存存储、闲置 30 分钟过期，重启即清空——这一点没有改变，多实例部署时不可用。
